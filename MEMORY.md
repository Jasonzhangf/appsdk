## Review ordering correction — 2026-08-20

- Review is a post-verification functional and architecture audit, not a substitute for tests, build, install, restart, online smoke, or real-sample evidence.
- Required order for new candidates: keep the candidate tree uncommitted -> run candidate verification -> DSH Review; use Codex Review only when DSH is explicitly unavailable -> after explicit PASS create the candidate commit -> rerun unchanged-source effectiveness -> merge/queue.
- A review run before candidate verification, or against a tree changed after verification/review, is stale and cannot be used as evidence. This rule is encoded in the global AppSDK governance skill and the `0.1.4-beta.1` Codex/WRAI.TH beta skill/docs.

## Collab design decisions — 2026-08-26

- The first registered worker remains the intentional project-local `master`; this is a bootstrap policy, not an audit defect. Do not replace it with controller election or a lease unless Jason changes the policy.
- The framework owns sender identity. `Send` callers must not supply an arbitrary `from`; the daemon/session layer derives and injects the authenticated sender before recording the message.
- Collab is deliberately light-coupled: durable mailbox/journal is the truth, and communication should interrupt reasoning only for actionable requests, task assignment, required replies, blockers, or explicit state changes. Informational notifications stay available in the inbox and should not wake the agent by default.
- Codex-to-Codex communication must also pass through collab and its governance rules. Codex App Server/TUI protocol may serve only as the transport or wake-up adapter; native `spawn_agent`/`send_input`/`wait` semantics must not bypass collab task, message, identity, evidence, and quiet-delivery rules.
- Collab design hierarchy: (1) collaboration rules are above communication; (2) communication is a capability that must obey collaboration rules; (3) communication is intentionally restrained—evaluate actionability and interruption cost before sending/waking, so agent reasoning is not needlessly interrupted.
- Codex App Server activity should be used as collab presence input: probe/observe whether a bound Codex session is active, idle, blocked, not loaded, or unknown before deciding delivery. Offline handling may return a protocol-level queued/deferred status and prepare mailbox delivery for reconnect, but must never fabricate an agent reply or bypass collab rules.
- Target closed loop: Codex agents are managed through collab MCP; AppServer RPC is the only Codex communication and state-sensing path. Heartbeat may probe/wake/resume a bound Codex session but reports `woken`, `resumed`, `unavailable`, or `queued` explicitly. Non-Codex agents may use tmux wakeups with mailbox durability; Codex-to-Codex durable mailbox/journal remains message truth and RPC is transport.
- Registration design: register one project-scoped identity and runtime session with an explicit AppServer owner/endpoint, verified `session_id` and `thread_id`, and optional pane identity for last-resort recovery. Codex `thread_id` is required RPC route identity, not a transport capability. Non-Codex agents may use their declared tmux or mailbox channels. Agents call the unified collab interface; collab resolves only the transport allowed by the current runtime contract.
- Capability correction — Codex TUI does not expose the Codex Desktop thread tools such as `send_message_to_thread`, `read_thread`, or `wait_threads`. Never infer Codex communication capability from the runtime name. A TUI agent must report only tools/interfaces actually visible in its own context; absent a verified explicit shared AppServer bridge, it must not register a Codex RPC endpoint. Desktop-only thread tools are not evidence for TUI capability.
- Codex source audit — upstream Codex has internal model tools `send_message`, `followup_task`, `send_input`, `resume_agent`, `wait_agent`, and `list_agents`, registered by `core/src/tools/spec_plan.rs` only when collaboration/multi-agent features are enabled. These are not named `send_message_to_thread`, and they target Codex agent paths managed by the internal `AgentControl`; they are model tool exposure, not automatically available to the TUI agent as external APIs. The TUI uses an embedded/local-daemon/remote App Server client internally; its client has `thread/list`, `thread/read`, `thread/resume`, and `turn/steer`, but a normal TUI does not expose those client methods as agent-callable tools. Collab integration must therefore detect the actual exposed tool list or an explicitly configured App Server bridge, not infer it from TUI source presence.
- Registration correction — communication capabilities are normalized and owned by collab; the target receives a projection of the normalized capability set. Any MCP server may provide outbound send, so sender transport is not the primary registration distinction. The critical target capability is arrival notification/delivery (push, wake, or only pull), which determines whether a message can reach the target without an agent actively polling. Do not update the collab skill with unimplemented capability schemas or interfaces; implement and test the protocol first, then update the skill from verified behavior.

## Verified Codex TUI native communication correction — 2026-09-24

- Two independent Codex TUI clients successfully used native AppServer `turn/start`, `turn/steer`, `thread/queue/add`, `thread/read`, `thread/turns/list`, and `thread/queue/list` when both attached to the same isolated local AppServer endpoint. `codex queue --thread <threadId> --remote unix:// --profile gcm` also queued to the other TUI; that TUI executed the unique marker. Full recorded evidence: `docs/codex-tui-collab-architecture.md` and `/tmp/ac27/RESULTS.md`.
- Therefore thread-ID-addressed native communication is proven within the owning AppServer. `threadId` alone does not locate a thread in another independent AppServer; the route must also identify the AppServer owner/endpoint. Cross-owner and cross-host routing remain unverified.
- tmux was only the experiment harness for hosting/observing the TUI peers. RPC responses, AppServer state reads, and target TUI output proved prompt execution; tmux did not carry the payload. This was not a Collab mailbox receive/ACK receipt.
- Corrects the earlier capability caution: normal TUI prompting does not itself expose appserver methods as model tools, but an explicitly configured shared AppServer RPC endpoint provides an external native bridge. Do not infer that bridge from a TUI thread ID; require an endpoint and daemon self-check.
- Target AppSDK design is AppServer-RPC-only for communication and state sensing, with composite one-round-trip registration of runtime `sessionId`/`threadId`, explicit AppServer endpoint/owner, and optional tmux pane/server identity. tmux is only the last-resort identity recovery anchor when both runtime IDs are unavailable; it never carries messages or proves presence. Runtime IDs come from the live runtime and are never synthesized or derived from each other. Conflicting or ambiguous evidence fails closed.
- Codex default `Embedded` TUI mode uses `AppServerClient::InProcess`, with internal request/event channels and no endpoint available to an independent Collab daemon. Codex `--profile` is a daemon-exclusion condition for the implicit shared local daemon. Therefore `codexp use gcm` alone does not connect a TUI to a shared AppServer; native Collab RPC requires an explicitly shared reachable endpoint, and registration must verify thread/session/project against that owner before mutation. Codex source baseline: `/Users/fanzhang/code/codex` HEAD `40eac3ce8a0c10cbcb9db910d529355eb2f8fc09`.
- Collab remains owner of durable identity, role, journal, mailbox, subscriptions, attempts, and consumption receipts. AppServer is transport and Codex state owner. RPC accepted != consumed; only a message-bound `collab recv`/ACK closes Collab consumption. Pane presence/activity is not used for Codex status or consumption.
- Current-source implementation (2026-09-24, in-progress candidate): production Collab now compiles `adapters::codex_app_server`, `init` submits the explicit AppServer candidate, daemon admission verifies the shared owner before binding, notification routes through the owning AppServer, and status sensing uses `thread/read`. tmux remains a last-resort recovery anchor; the two-TUI live acceptance is still pending. Design record and implementation DAG: `docs/codex-tui-collab-architecture.md`.
- The same source audit found that `async-result` was present in notification event/config/MCP/docs contracts but had no executable producer under `collab/src`. Companion candidate `codex/collab-dag-close-20260924` removes the unsupported public contract; its full Collab suite passed (794 unit tests, 11 MCP tests, 1 isolated tmux e2e; one ignored), format/diff checks and `cargo build` passed. Retain actual peer results through durable direct-message/task paths unless a concrete async-operation owner is introduced.
