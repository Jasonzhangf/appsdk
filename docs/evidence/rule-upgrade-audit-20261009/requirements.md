# 用户需求来源与本次范围

来源：当前 Codex 对话 01a123de-ff54-76a2-9265-4f8f8d862230，2026-10-09 用户消息。以下原文是编排者从本会话保存，供 reviewer 对照；不是 agent 新增需求，也不代表机器审批账本。

1. “我现在觉得 我们应该审计一下目前测试的全局和局部 以及测试的流程 我认为现在我们的测试中，有太多的测试是改一个地方就全局跑，这非常非常影响我们的效率。我们其实应该根据风险进行测试。也就是说，一个变更在没有提交的时候，要求做的测试仅仅是完成它影响范围内的测试，而不是每一次都跑全量。全量是在 release 的时候跑。你觉得呢？？”
2. “那我们现在有两个问题：第一个，我们当前这个规则需要修改，这相对来说还比较简单。第二个，更新 SDK 以后，可能需要要求其他项目进行规则变更。关于这个规则变更，我们需要考虑一下如何把当前已有的全局规则进行缩减和精简。这其实是要让他们做一次审计和重新做的，这一点需要考虑到。”
3. “我们的 AppSDK 需要做实际的规则变更和升级吗？”
4. “那我们自己要进行实际的规则变更升级 包括 skills 然后再去安装这些规则变更 最后再进行发布 而且你可以看一下我们现在的全局规则 理论上我们应该根据这个规则 对我们自身的架构和代码进行一次完整的审计 要使用最小充分结构和最小必要流程”
5. “你现在任务的推进 要按照最新的规则和 skill 进行编排 计划以及 review”

本次适用验收：AppSDK 规则/Skills/升级建议和实际 CI 流程体现风险选测与 release 完整门禁；升级建议要求项目 owner 审计并精简旧规则及实际执行入口，保持单一正文归属、已有授权和可选 Guidance；自身活跃架构审计的覆盖、保留/删除依据、未验证边界可追溯；修复已确认影响升级的边界；source → 正式安装 → canonical CLI/Skills 行为 → 独立有效 review → 集成/main/remote → 公开发布 → 自有资源回收闭环。

用户没有授权降低测试断言、绕过 CI/hook、伪造 PASS、清理其他任务资源或无关生产状态。本任务采用一次完整 AppSDK 交付候选；Collab/DAGpipe 审计结果保留，不自动同时发布第二产品，不将静态疑点当根因。全局规则已于前序实际修订；本次项目实现不建立第二全局规则真源。
